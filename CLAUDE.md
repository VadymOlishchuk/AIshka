# AIshka

Навчальна платформа: персональний план уроків, який збирається з відповідей
онбордингу, збірка проєкту зі слотами, плеєр уроку з квізами й прогрес.
Повна документація — «План збірки LMS», частина 4 (артефакт). Тут — лише те,
що потрібно щодня.

## Пріоритети

Платформа й наповнення першими. Маркетингова воронка на 28 кроків, Stripe і
AI-чат — наступні етапи; схема БД і гейт доступу вже готові до них.

## Структура

Nx-монорепо, pnpm workspaces.

```
apps/backend   Fastify 5 на Node 24 — REST під /api, cookie-auth, конверт відповіді
apps/main      платформа: React 19 + Vite + react-router, SPA. Вхід, онбординг, дашборд
apps/landing   лендінги й воронки на піддоменах: вітрина, реєстрація, згодом оплата.
               Після реєстрації веде на main; бекенд і сесія спільні (COOKIE_DOMAIN)
libs/ui        спільний UI платформи й лендінгів: токени, примітиви, іконки, AuthForm,
               клієнт API. Стиль лендінгу = стиль платформи, бо код один
libs/core      домен: auth, plan, progress, build, content, Prisma-клієнт.
               Без React і без Fastify — це шов для другого клієнта
prisma/        схема й міграції; клієнт генерується в libs/core/src/generated
content/       курси, проєкти, онбординг — json у git
scripts/       content:check / content:sync / project:sync / emoji:sync
```

## Команди

```
pnpm dev:all                # піднімає Postgres у Docker, чекає healthcheck, далі backend :3001,
                            # main :5173, landing :5174; Vite проксіює /api
pnpm db:up / db:down        # лише база, коли треба окремо
pnpm docker:prod            # прод: main :3000, landing :3100 (nginx) -> backend -> db
pnpm db:migrate             # міграція після зміни schema.prisma
pnpm content:check          # гейт публікації без запису в БД
pnpm content:sync           # валідація + імпорт контенту й проєктів у БД
pnpm emoji:sync             # об'ємні значки Fluent для нових емодзі в контенті
pnpm typecheck              # tsc по всіх проєктах через nx
```

**Після `db:migrate` перевір, що backend перезапустився.** Клієнт Prisma генерується
в `libs/core/src/generated`, tsx watch зазвичай підхоплює це сам; якщо сторінки
віддають старі дані без нового поля — перезапусти `pnpm dev:all`. Двічі втрачали
на цьому час ще на Next.

## Рішення, які не переобговорюємо

- **Домен у `libs/core`** без React і Fastify. Роути в `apps/backend` тонкі: розбір
  вводу, виклик домену, конверт. Логіка в роуті — помилка.
- **Лендінги — окремий застосунок, не окремий стиль.** Кожна нова воронка — маршрут
  в `apps/landing`, компоненти — з `libs/ui`. Реєстрація й оплата там, платформа — в main.
- **Контент живе в git** (`content/*.json`), а не редагується руками в БД.
  `content:sync` валідує й заливає. Це дає код-рев'ю на контент і відкат одним `git revert`.
- **Гейт публікації** (`libs/core/src/content/course.ts`) — обов'язковий. Урок, який його
  не пройшов, у базу не потрапляє. Без нього каталог швидко наповнюється дефектами.
- **Прогрес прив'язаний до трійки** `(userId, lessonId, courseId)`. Той самий урок
  у різних курсах — різні досягнення.
- **Доступ перевіряється двічі**: loader у `apps/main/src/router.tsx` вирішує маршрут,
  `requireActiveAccess()` у кожному API-хендлері захищає ресурс. Приховати кнопку — не захист.
- **Формат відповіді API** — `{ok:true,data}` / `{ok:false,error:{code,message,fields?}}`.
  Клієнт ніколи не парсить текст повідомлення, тільки `code`. Помилки домену — `AppError`.
- **Токени**: короткий JWT у cookie `at` (15 хв) + непрозорий refresh у `rt` (30 днів,
  ротація з виявленням повторного використання). Обидві cookie — HttpOnly. Клієнт на
  перший 401 сам кличе `/api/auth/refresh` і повторює запит.
- **Docker лише для Postgres і проду.** Розробка — `pnpm dev:all` на хості: dev-compose
  з bind-mount і томом node_modules пробували, він не вартий своїх граблів.
- **Один домен для браузера**: у dev Vite проксіює `/api`, у prod — nginx. Тому CORS
  немає і не має з'явитися. Між піддоменами main/landing сесію несе cookie на
  батьківському домені, а не токен у URL.

## Воронка входу

Єдиний спосіб потрапити в продукт — через лендінг (`apps/landing`):

```
/start            email + ім'я      -> POST /api/checkout/start      -> User без пароля + Order pending
/checkout/:id     оплата            -> POST /api/checkout/:id/complete (stub) або Stripe-вебхук
                                     -> Order paid, Subscription active, токен на пароль
/set-password     пароль            -> POST /api/auth/password/set    -> сесія в cookie
-> MAIN_URL/onboarding               платформа відкривається вже з входом
```

`/api/auth/register` немає навмисно: акаунт з паролем без оплати — обхід воронки.
Заглушка оплати існує лише при `PAYMENTS_PROVIDER=stub`; зі Stripe маршрут
`/complete` не реєструється взагалі, а `completeCheckout()` кличе вебхук.
Акаунт без пароля не входить ніколи, але перевірка коштує стільки ж часу.

## Правила контенту

Урок: 8–14 блоків, 400–1400 слів, текстовий блок ≤110 слів, обов'язкові квіз і summary
з тізером. Варіанти квізу вирівняні за довжиною — інакше правильну відповідь видно на око.
Банер помилки дає напрямок думки, а не відповідь. Повні правила — у розділах 21–22 плану збірки.
