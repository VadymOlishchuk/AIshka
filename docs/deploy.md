# Перенос на власні акаунти

Локальна розробка лишається на Docker. Supabase і Vercel — тільки для проду.
GitHub лишається той самий.

## Що треба створити

| Сервіс | Навіщо | Тариф на старті |
|---|---|---|
| **Supabase** | Postgres замість локального Docker | безкоштовний |
| **Vercel** | хостинг застосунку | безкоштовний (Hobby) |
| **Resend** | листи відновлення пароля | безкоштовний до 3000/міс |

Реєструй їх на ту пошту, під якою хочеш вести цей продукт. Vercel і Supabase
дозволяють увійти через GitHub — якщо так робиш, це прив'яже їх до наявного
GitHub-акаунта, що нормально, бо репозиторій лишається там же.

## Крок 1 — Supabase

1. New project. Регіон бери найближчий до аудиторії, не до себе.
2. **Пароль бази показується один раз** — збережи одразу в менеджері паролів.
3. Project Settings → Database → Connection string. Потрібні ДВА рядки:

   - **Session pooler** — сюди ходить застосунок:
     `postgresql://postgres.<ref>:<пароль>@aws-0-<region>.pooler.supabase.com:5432/postgres`

   - **Direct connection** — сюди ходять лише міграції:
     `postgresql://postgres:<пароль>@db.<ref>.supabase.co:5432/postgres`

4. Створи локально файл `.env.production` (він у .gitignore, в git не поїде):

   ```
   DATABASE_URL="<session pooler>"
   DIRECT_URL="<direct connection>"
   AUTH_JWT_SECRET="<новий, згенерований: openssl rand -base64 48>"
   NEXT_PUBLIC_APP_URL="https://<домен, який дасть Vercel>"
   BILLING_ENABLED="false"
   ```

**Чому два рядки.** Міграції створюють таблиці й беруть блокування — через
транзакційний пул це не працює. Застосунок навпаки має ходити через пул, бо
безсерверні функції відкривають багато коротких з'єднань, і пряме підключення
вичерпає ліміт.

**Секрет має бути іншим, ніж локальний.** Якщо однаковий — токен, виданий на
твоїй машині, працюватиме на проді.

## Крок 2 — міграції та контент

Після того як `.env.production` існує:

```
pnpm db:deploy:prod       # застосовує міграції до Supabase
pnpm content:sync:prod    # заливає 172 уроки
```

Обидва читають `.env.production` замість `.env` — це робить змінна
`DOTENV_CONFIG_PATH`, окрема залежність не потрібна.

`migrate deploy` застосовує наявні міграції без інтерактиву — саме те, що
потрібно для чужої бази. `migrate dev` на проді не запускати ніколи.

## Крок 3 — Vercel

1. Add New → Project → імпортуй `AIshka` з GitHub.
2. Framework Next.js визначиться сам, збірку не чіпай.
3. Environment Variables — додай ті самі п'ять змінних, що в `.env.production`.
4. Deploy.
5. Після першого деплою онови `NEXT_PUBLIC_APP_URL` на справжній домен і
   передеплой — інакше посилання в листах вестимуть у нікуди.

## Чого НЕ робимо

**Не переносимо авторизацію на Supabase Auth.** У нас власна: argon2, JWT у
HttpOnly cookie, ротація refresh-токенів. Supabase тут використовується тільки
як Postgres. Перехід на їхній Auth — це переписування, а не налаштування.

**Не тримаємо медіа в Supabase Storage.** 3 МБ ілюстрацій у `/public` Vercel
віддає з власного CDN швидше. Сховище знадобиться, коли з'явиться відео.
